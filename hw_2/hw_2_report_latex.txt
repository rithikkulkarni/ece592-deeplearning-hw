\section{Data Augmentation Implementation (Question 1)}

I implemented \texttt{train\_tfm} by layering four augmentation transforms on top of the required resize/tensor conversion, resizing to $128\times128$ (matching the sample code's default, so no changes were needed to the classifier's flattened input dimension):

\begin{lstlisting}[caption={Final train\_tfm}, label={lst:train-tfm}]
train_tfm = transforms.Compose([
    transforms.RandomResizedCrop(128, scale=(0.5, 1.0)),
    transforms.RandomHorizontalFlip(),
    transforms.RandomRotation(35),
    transforms.ColorJitter(brightness=0.4, contrast=0.4, saturation=0.4, hue=0.1),
    transforms.ToTensor(),
])
\end{lstlisting}

In order to confirm that this process fulfilled the requirements of having 5+ visibly different results, I provided an example of applying \texttt{train\_tfm} to one training image 5 times. The results of this application are depicted in \autoref{fig:aug-grid}. In addition, to make sure that the variance in these images are not only visibly but also metrically significant, I computed the mean absolute difference (pairwise) between all 5 of the output tensors that the transformation process gave, and the range of these differences was 0.12-0.30. This confirms that each pair is significantly different from one another, instead of being trivially adjusted.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{q1_augmentation_grid.png}
    \caption{Original image (leftmost) and the 5 independent applications of \texttt{train\_tfm.}}
    \label{fig:aug-grid}
\end{figure}

Each of the four individual transformations that I've layered in \texttt{train\_tfm} target a different potential source of overfitting, and are all pulled directly from the \texttt{torchvision.transforms} library:

\begin{itemize}
    \item \textbf{RandomResizedCrop} randomly cuts out (crops) some part of the image, which I've set to be 50-100\% of the image area, and then resizes what is left of the image back to $128\times128$. This aids the model by preventing it from becoming dependent on the important object in the image being perfectly centered or taking up the entire frame of the image. This helps counter overfitting to the exact composition of training images.
    \item \textbf{RandomHorizontalFlip} simply mirrors the image randomly with a 50\% probability (coin flip). Since photos of food have no dependence on being flipped left or right (they're still the same thing no matter the angle), this randomized flip aims at helping the model being left-right invariant.
    \item \textbf{RandomRotation(35)} rotates the image by up to $\pm35^\circ$. This aims to help counter the model overfitting to the exact camera angle or tilt that its training images happened to be taken at. I purposefully chose a relatively small range for the angle so I could avoid accidentally distorting the identity of the food, since larger angles like a $90^\circ$ tilt could make things look entirely unnatural.
    \item \textbf{ColorJitter} will randomly perturb/mess with the brightness, constrast, saturation, and the hue of the image. This aims to prevent the model overfitting to specific lighting conditions or the whiteness balance of certain images. Since images of food can drastically vary in brightness and lighting, we want to help the model adapt to that in training.
\end{itemize}

The function \texttt{transforms.Compose}, which triggers the transformation, applies all four transforms every call in the same fixed order. None of the transformations are randomly skipped, except for the chance that \texttt{RandomHorizontalFlip}'s coin flip results in no change to the image. The only variance introduced in this process comes from each of the transformations having their own individual random parameters that are applied within each of the four layers.

\section{Achieving Baselines (Enhancing Accuracy)}

\subsection{Initial Experimentation}

After implementing data augmentation as described above, I ran my Experiment 1 in an attempt to understand where I was at in comparison to the 4 primary baselines listed in the assignment instructions. Using the default epoch count of 8, I ran an experiment on Kaggle's T4 GPU using the sample code's defaults left unchanged (batch size of 64, Adam optimizer with a learning rate of 0.0003). This run reflects the sample architecture with only the addition of the data augmentation from Q1, so no deliberate tuning has been done for this experiment (\autoref{fig:exp1}).

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp1_curve.png}
    \caption{Experiment 1: training vs. validation accuracy per epoch.}
    \label{fig:exp1}
\end{figure}

Experiment 1 achieved a best validation accuracy of 0.496 at epoch 7, which falls very short of even the Simple baseline described by the assignment instructions (0.637). This is likely due to the low epoch count, as both the training and validation losses were still steadily decreasing all the way through epoch 8. An epoch count of 8 was simply too short. Since augmentation has the known tradeoff of gaining better generalization with slower convergence, it makes sense that we'd observe these results with so few epochs.

To put this to the test, I performed another experiment (Experiment 2) with the same exact configuration as Experiment 1, but with the epoch count raised to 30 and the patience value raised from 5 to 8. I chose to also increase the patience value because the validation accuracy in Experiment 1 was quite noisy between epochs, which meant that the low patience value could have risked an early stop to trigger on some temporary dip rather than a true convergence/plateau.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp2_curve.png}
    \caption{Experiment 2: training vs. validation accuracy per epoch.}
    \label{fig:exp2}
\end{figure}

Experiment 2 did much better, reaching a best validation accuracy of 0.658 at epoch 25 (\autoref{fig:exp2}). This clears the Simple baseline of 0.637, but doesn't quite achieve the Medium baseline of 0.700. For experiment 2, the full 30 epochs ran without reaching an early stop trigger. The longest streak without a new best was in the last 5 epochs. Despite this being decently under the patience of 8, the last 10 epochs together were all stuck in a validation accuracy between roughly 0.61 and 0.66 without any signal that it would continue upward. Additionally, the training accuracy kept increasing steadily, which meant that the gap between training and validation accuracy eventually reached 0.715 to 0.643. This is a sign that in the later epochs, the model gradually began to overfit.

Since I've already done data augmentation, I wanted to try and reach the Medium baseline before continuing with other architecture changes; however, since the later epochs showed signs of overfitting, I realized that adding more epochs would not help, and the model architecture may be the bottleneck here.

\subsection{New Architecture: ResNet18}

Next, I took the suggestion for reaching the strong baseline and swapped in a predefined architecture rather than continuing to tune a CNN from scratch. Experiment 3 shows results from running a ResNet18 from \texttt{torchvision.models} with no pretrained weights. I kept all other configurations from Experiment 2 except epoch count and patience, which I switched to 40 and 10 respectively.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp3_curve.png}
    \caption{Experiment 3 (ResNet18): training vs. validation accuracy per epoch.}
    \label{fig:exp3}
\end{figure}

This experiment reached an overall best validation accuracy of 0.691, which is almost at the Medium baseline. This is a clear improvement over 0.658 from Experiment 2. One important observation is that Experiment 3's validation accuracy seemed to fluctuate a lot even in the later epochs (for example, 0.685 to 0.652 in epochs 31-32 and 0.633 to 0.683 in epochs 35-36) (\autoref{fig:exp3}).

Since I never tuned the learning rate from when we were training a CNN from scratch, this learning rate could be too high for the batch normalization and residual connections that ResNet18 has built into its architecture. This is the most likely explanation I came up with for this observation.

\subsection{Further Tuning: Learning Rate}

After observing large fluctuations in validation accuracy from epoch to epoch in the last experiment, I decided to lower the learning rate from 0.0003 (sample default) to 0.0001. Additionally, I raised the epoch count from 40 to 60 and raised patience from 10 to 15 so I could see how the model does with more time.\

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp4_curve.png}
    \caption{Experiment 4 (ResNet18, lr=0.0001): training vs. validation accuracy per epoch.}
    \label{fig:exp4}
\end{figure}

Experiment 4 reached a best validation accuracy of 0.680 at epoch 48 (\autoref{fig:exp4}). Surprisingly, slightly \emph{lower} than Experiment 3, despite running 20\% more epochs. The training ran the full 60 epochs without hitting an early stop trigger.

To check metrically if the lower learning rate actually helped with the instability I observed in the last experiment, I calculated the absolute average epoch-to-epoch change over the last 30 epochs. This absolute average change came out to be 0.0146, which is better than the previous experiment's 0.0262 (roughly a 44\% decrease). This means that the learning rate seems to have reduced the instability, but convergence is slower.

The real issue here is that the model seems to be overfitting in the later epochs. The training accuracy increased steadily the entire time up to 0.779, but the validation accuracy start flatlining in the 0.62-0.68 range for a long time. This is a significant gap in training and validation accuracy that signals the model is overfitting.

\subsection{Regularization: Dropout and Weight Decay}

To try and fight the overfitting, I decided to add dropout of 0.3 and raised the weight decay from 1e-5 to 1e-4 in the optimizer. I kept other parameters such as the learning rate of 0.0001 and the epoch count/patience of 60/15 unchanged. This way, I can see if regularization actually helps.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp5_curve.png}
    \caption{Experiment 5 (ResNet18, dropout=0.3, weight\_decay=1e-4): training vs. validation accuracy per epoch.}
    \label{fig:exp5}
\end{figure}

Experiment 5 achieved a best validation accuracy of 0.679 near the end at epoch 59 (\autoref{fig:exp5}). This is almost identical to the best accuracy from Experiment 4, even though I added dropout and a stronger weight decay. It seems that at this medium dose, regularization was unable to improve peak accuracy.

It also did not seem to fix the overfitting issue. The training accuracy still continued to climb higher while validation accuracy plateaued. The final gap at epoch 60 was comparable to the same gap in Experiment 4.

This signals that perhaps the dropout were too little to have some meaningful effect in countering the overfitting problem. The next step is to be more aggressive with the regularization and see if that helps.

\subsection{Stronger Regularization}

For Experiment 6, I raised the dropout from 0.3 to 0.5 and weight decay from 1e-4 to 1e-3 (another 10x) to potentially address the accuracy and overfitting issues. All of the other parameters from before were kept the same.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp6_curve.png}
    \caption{Experiment 6 (ResNet18, dropout=0.5, weight\_decay=1e-3): training vs. validation accuracy per epoch. Dashed green line marks the Medium baseline (0.700).}
    \label{fig:exp6}
\end{figure}

This experiment achieved a best validation accuracy of 0.707 at epoch 58 (\autoref{fig:exp6}). This is the first time I've cleared the Medium baseline across any of my prior experiments.

It seems that this time, the stronger regularization did what it was actually supposed to do. The gap between training and validation accuracy stayed smaller throughout all of training. This confirms what I suspected after observing Experiment 5.

Despite having made some progress here, though, there is still a long way to go before the Strong and Boss baselines. Some different techniques may have to be introduced to achieve this.

\subsection{Cross Validation \& Ensemble}

For my next experiment, it seemed I needed to try something new. I decided to do a 3-fold cross validation on just the training set (10,000 samples) and create an ensemble out of the 3 individual models. The final ensemble would then be tested on the validation set of 3,643 samples to judge its final validation accuracy. This cross validation is an attempt at adding variance to the model to catch case samples that otherwise wouldn't be caught.

I kept the same ResNet18 model and ``recipe'' for all 3 folds. Any real difference in each fold will end up coming from the data augmentation adding variance rather than the actual training configuration. Each fold trains an individual model on $\frac{2}{3}$ of the original 10,000 samples and then validates on the remaining $\frac{1}{3}$ (\autoref{fig:exp9}). Once all 3 folds are done training, each fold's model gets evaluated along with the ensemble of all 3 together. This ensemble averages their predicted class probabilities/predictions and the result is taken as the final prediction. This validation is taken on the validation set of 3,643 samples that were not used for training.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{exp9_curve.png}
    \caption{3-fold cross-validation: training vs. fold-validation accuracy per epoch for each of the 3 folds. Fold 2 triggered early stopping at epoch 47.}
    \label{fig:exp9}
\end{figure}

The individual accuracies of each fold on the validation set were 0.648, 0.624, and 0.592. The ensemble of all three folds reached 0.676. Every single result here is worse than our previous best validation accuracy of 0.707. The most likely explanation for this result is that each fold is getting far fewer training samples (6,667 vs 10,000), since I held out the remaining samples for individual fold validation.

This experiment is quite valuable despite the negative result. This pushes me away from immediate cross validation and towards pushing farther with a single model: perhaps a deeper architecture like ResNet34 instead of ResNet18 is the answer.

\subsection{Scaling Up: ResNet34}

I decided to set cross validation aside as a potential later configuration. I swapped ResNet18 for ResNet34, which is a deeper version of similar architecture, and gave it much more time for training with increased patience (150/25). All the other parameters such as dropout, weight decay, and learning rate, were kept the same according to my previous best performing experiments.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp10_curve.png}
    \caption{ResNet34, 150 epochs (early-stopped at epoch 116): training vs. validation accuracy per epoch. Green line denotes the Strong baseline (0.814).}
    \label{fig:exp10}
\end{figure}

This run achieved a best validation accuracy of 0.738 at epoch 90, and reached an early stop trigger at epoch 116 (\autoref{fig:exp10}). This certainly clears my previous best validation accuracy of 0.707, which is a good start.

One thing I did notice here is that the model's steady improvement lasted far longer than any of the experiments with ResNet18. The best result wasn't achieved till epoch 90, which is a later epoch than the max for any previous runs. This makes sense since ResNet34 is a deeper model with more capacity and needs more epochs to actually make use of that capability.

Important to note is that training accuracy kept climbing all the way past 0.84 in the last epochs, which signifies that it began overfitting. However, switching architectures definitely helped increase validation accuracy in the long run.

\subsection{Learning Rate Schedule: Cosine Annealing}

If we take a look at the previous experiment's curves, the validation accuracy peaked at epoch 90 and then for the remainder of training drifted back down and plateaued, even though the training accuracy kept climbing. This looked like a flat learning rate wasn't quite giving the later epochs enough room to find a better minimum, so I decided to add a cosine annealing schedule for the learning rate where it now decays smoothly from a set starting value (0.0003) down to 0 over the entire course of training. I raised the learning rate to 0.0003 because the schedule is bringing it back down anyway. All other parameters were kept the same as before.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp11_curve.png}
    \caption{ResNet34 with cosine-annealing learning rate schedule, full 150 epochs (no early stopping): training vs. validation accuracy per epoch. Green line denotes the Strong baseline (0.814).}
    \label{fig:exp11}
\end{figure}

This run managed a best validation accuracy of 0.799 at epoch 147 (\autoref{fig:exp11}), and never triggered the early stopping. That's a huge jump from the previous peak of 0.738.

The shape of the curve is also quite different than before. Instead of peaking early, the validation accuracy kept climbing with the training accuracy for the entire run, which suggests that the learning rate schedule was working exactly as intended.

The training accuracy still ended up extremely high around 0.95 by epoch 150, so there's still an overfitting gap remaining that needs to be addressed. Unlike before, however, the overfitting isn't what is actively costing us in terms of validation accuracy.

\subsection{ResNet50 + Test Time Augmentation}

Since the previous experiment got quite close to the strong baseline, I just made two chagnes for this experiment to try and make another leap in validation accuracy: Since upgrading the ResNet model capacity from 18 to 34 made such a big difference, I upgraded to ResNet50, an even deeper version of the same architecture family. I kept every other training parameter different and added test time augmentation (TTA) at inference time, as suggested in the homework hints.

TTA means that instead of predicting on a single, unaugmented version of each image, I also run 5 separate randomly-augmented versions using the \texttt{train\_tfm} that I built in Question 1 to create various versions of the same image, averaging the prediction of the model of all 5 to get a final prediction. As the hint suggested, I weighted the augmented average 0.2 and the deterministic prediction 0.8.

Since TTA doesn't actually effect training, I added a separation validation step for it at the end, completely independent of the regular mid-training evaluation so as not to disrupt the current architecture.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp12_curve.png}
    \caption{ResNet50 with cosine-annealing learning rate schedule, full 150 epochs: training vs. validation accuracy per epoch.}
    \label{fig:exp12}
\end{figure}

The ResNet50 model by itself reached a new best validation accuracy of 0.813 at epoch 132, and ran the full 150 epochs without stopping early (\autoref{fig:exp12}). That's already an improvement on all previous experiments, and just short of the Strong baseline. Once TTA was added on top of this, the validation accuracy was pushed from 0.813 up to 0.819, surpassing the Strong baseline for the first time.

Both changes seemed to have contributed positively here. Switching to ResNet50 already closed a great deal of gap to the Strong baseline, and TTA gave the final push to get over it. The curve itself visually looks very similar to the previous experiment's, where validation accuracy goes up with the training accuracy for most of the run instead of what we had before in earlier experiments, where it peaked early. This makes sense, since I did not tweak the now-existing learning rate scheduler that was introduced in the previous experiment, only the underlying model itself.

\subsection{Real Ensembling: ResNet34 + ResNet50 + DenseNet121}

With only the Boss baseline of 0.874 remaining, pushing a single model any further seems unlikely. This brought me back to the ensembling I tried earlier, but this time doing it properly. My earlier attempt did so horribly because each fold only trained on $\frac{2}{3}$ of the training data, so each individual model was far weaker to begin with. This time, each individual model has been trained on the full training set of 10,000 samples individually.

I built a 3-model ensemble using the ResNet34 model from when I introduced an LR schedule, the ResNet50 model from the last experiment (TTA), and a newly trained DenseNet121 model that is from a different architecture family to hopefully introduce some diversity in coverage and aid the ensemble output. I trained DenseNet121 using the same parameters as my other experiments (dropout 0.5, weight decay 1e-3, learning rate schedule started at 0.0003, and 150/25 epochs/patience).

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp13_curve.png}
    \caption{DenseNet121 LR schedule, 150 epochs: training vs. validation accuracy per epoch.}
    \label{fig:exp13}
\end{figure}

Since I had already trained two of the models, new training only had to run on DenseNet121 (\autoref{fig:exp13}). I brought in the two previous ResNet models as Kaggle Datasets so that this run could load them in directly instead of retraining.

DenseNet itself reached a best validation accuracy of 0.798 at epoch 146. With TTA, the validation accuracies of each model were 0.807 (ResNet34), 0.821 (ResNet50), and 0.803 (DenseNet121). I then combined all of the TTA-blended probabilities using a simple, equal-weighted average (where each model contributes $\frac{1}{3}$, and got a validation accuracy of 0.845 on the validation set. This beats every individual model from before.

What was really interesting here is that DenseNet121 was actually the weakest out of all three models, but still meaningfully improved the overall ensemble because it helped patch the errors that ResNet models tend to struggle with.

I also tried weighing the ensemble by individual model accuracy instead of equal weights for every model, but this absolutely no measurable difference (still 0.845).

\subsection{Fourth Model: VGG16 + CutMix}

My next idea was to add a fourth member to the ensemble, for which I picked VGG16 with batchnorm, specifically because it has the most different architecture from the current three models I'm using. It has no skip connections at all, unlike ResNet or DenseNet. I also decided to try training it with CutMix, which cuts out a random rectangular area from one training image and introduces it to another training image. This mixes image labels proportionally to how big the patch was. I applied this for half the training batches, using the standard settings that I found in the CutMix paper \citep{yun2019cutmix}. All hyper-parameters in this training, however, stayed the same as my other experiments.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{exp15_curve.png}
    \caption{VGG16 (batchnorm) + CutMix, cosine LR schedule, 150 epochs (no early stopping): training vs. validation accuracy per epoch.}
    \label{fig:exp15}
\end{figure}

VGG16 achieved a best validation accuracy of 0.836 at epoch 149 (\autoref{fig:exp15}). With TTA, this went up to 0.843, making it the single strongest individual model performance so far. CutMix seems to have helped substantially, both in keeping the model steadily improving, and in just raw accuracy.

I then combined all four models (ResNet34, ResNet50, DenseNet121, VGG16+CutMix) into an equal weighting ensemble, which achieved a validation accuracy of 0.863. With accuracy-based weighting, it improved to 0.864, but that is almost negligible improvement. It seems the fact that VGG16 had a bigger gap in performance from the other three made the accuracy-based weights actually matter.

\section{Final Accuracy}

My best-performing result is the 4-model ensemble described above: ResNet34, ResNet50, DenseNet121, and VGG16 (trained with CutMix), each trained independently on the full 10,000-image training set, combined via accuracy-based weighting of their test-time-augmented predictions. This ensemble reaches a \textbf{final validation accuracy of 0.864} on the 3,643-image validation set.

This clears the Simple (0.637), Medium (0.700), and Strong (0.814) baselines, and falls short of the Boss baseline (0.874) by about 0.01. I plan to run one more experiment to try to close this remaining gap, but 0.864 is my result as of this report.

Since this ensemble is built by combining four independently-trained models rather than a single continuous training run, there isn't one ``best epoch'' train/validation accuracy pair for the ensemble itself. For that reason, I'm also reporting the training and validation accuracy of my single best-performing individual model, VGG16 (trained with CutMix), at its own best epoch (epoch 149): a \textbf{training accuracy of 0.745} and a \textbf{validation accuracy of 0.836} (before TTA and ensembling -- 0.864 is the final combined number reported above).

\section{Visual Representations Implementation (Question 2)}

For this section, I was instructed to use t-SNE (dimensionality-reduction technique) to visualize the embeddings of certain classes at different layers in the inference of the final model, which in this case, is the VGG16 + CutMix model that achieved a validation accuracy of 0.843. The goal is to see whether the tight clustering of each food class gets better at deeper layers, which would signal that the network is getting better at class discrimination as the data moves through it.

VGG16's convolutional feature extractor (\texttt{model.features}) is a single flat \texttt{nn.Sequential} stack of layers, unlike ResNet or DenseNet which use sub-blocks that are named. This made it so that I could extract the output of some intermediate layer by using the layer's index, similar to how the original starter code was doing it for the from-scratch CNN. There were 5 convolutional blocks in VGG16, and each ended in a max-pool layer, so I defined ``mid'' as the end of block 3 (index 24) and ``top'' as the end of block 5 (index 44). I did this so that it would roughly split the network into thirds.

For each of these two mid/top layers, I ran every single image in the validation set through the model up to that layer, then flattened the feature maps into a single vector for an image, and applied t-SNE to project them into a 2D space. The mid-layer features are extremely high-dimensional, so before doing t-SNE, I reduced them to 50 dimensions with PCA (Principal Component Analysis) before running t-SNE. I did this because t-SNE does pairwise computation which would be incredibly slow with so many dimensions. I was recommended this by scikit-learn's documentation of t-SNE.

\begin{figure}[htbp]
    \centering
    \begin{subfigure}{0.48\textwidth}
        \centering
        \includegraphics[width=\textwidth]{q2_tsne_mid.png}
        \caption{Mid layer (end of block 3)}
    \end{subfigure}
    \hfill
    \begin{subfigure}{0.48\textwidth}
        \centering
        \includegraphics[width=\textwidth]{q2_tsne_top.png}
        \caption{Top layer (end of block 5)}
    \end{subfigure}
    \caption{t-SNE visualization of VGG16's learned representations on the validation set, colored by true class (11 food classes).}
    \label{fig:q2-tsne}
\end{figure}

This visual result definitely matches my expectations (\autoref{fig:q2-tsne}). At the mid layer, most of the classes are still amongst the huge blob, and only some of the classes are moving to their own specific regions. At the top layer, there is a stark difference where each class has a clearly isolated cluster, even the ones that did not show signs of such behavior at the mid layer.

This visually confirms that the network progressively transforms the information from image pixels into information that are specialized for classifying these 11 classes of food.
